# db — agent guide

Models, sessions and CRUD functions shared by every server. Commands for migrations
and tests are in the root `AGENTS.md`.

| Path | Role |
|---|---|
| `models.py` | SQLAlchemy 2.0 models, each paired with a Pydantic validator |
| `async_session.py` | The async engine and `async_session`, used by the FastAPI servers |
| `sync_session.py` | A smaller sync engine for pandas and other blocking code |
| `crud/` | All queries, one module per area, re-exported from `crud/__init__.py` |
| `pool_monitor.py` | Pool occupancy and event-loop lag logging |

## Adding a model

- Inherit `Base, IdMixin` and define the validator right below the model:
  `FooValidator: TypeAlias = sqlalchemy_to_pydantic(Foo)`. The validator mirrors the
  columns only; relationships aren't included. A non-nullable column with no default
  becomes a **required** field, so adding one breaks every place that builds that
  validator by hand.
- Store datetimes as naive **UTC** (`DateTime`, not `DateTime(timezone=True)`). Get
  "now" from `rsptx.response_helpers.core.canonical_utcnow()`.
- Then write a migration (below). Tests won't catch a missing one: `init_test_db`
  builds the test schema with `create_all` from the models, never from migrations.

## Adding a CRUD function

- Put it in the matching `crud/<area>.py`, then import it in `crud/__init__.py`
  **and** add its name to that module's `__all__` block. Callers always import from
  `rsptx.db.crud`. A name imported but missing from `__all__` fails flake8/ruff (F401).
- Return validators, not ORM objects: `FooValidator.from_orm(row)`. `from_orm(None)`
  returns `None` (see `BaseModelNone` in `rsptx/validation/schemas.py`), so
  `one_or_none()` results can be passed straight through.
- Read with `async with async_session() as session:`; write with
  `async with async_session.begin() as session:`, which commits on exit.
- **Each CRUD call is its own transaction.** Two calls from a router aren't atomic,
  and a row one call commits is visible to the next call immediately. When several
  writes must succeed or fail together, do them in one function and one `begin()`
  block (`replace_user_experiment_entries` in `crud/question.py` is an example).

## Unique indexes and check-then-insert

Many functions fetch a row, then update it or insert a new one. Two concurrent
requests can both see "no row" and both insert, and the second violates the unique
index. Where duplicates are expected, use Postgres `INSERT ... ON CONFLICT` (see
`pg_insert(...).on_conflict_do_update` in `crud/telemetry.py`) instead of catching
`IntegrityError`. A caught-and-logged `IntegrityError` hides bugs where the lookup and
the insert use different keys; see `components/rsptx/grading_helpers/AGENTS.md`.

## Migrations

`migrations/env.py` uses `DEV_DBURL` (or `DBURL` when `SERVER_CONFIG=production`).
Before applying an autogenerated migration, check:

- **It contains only your change.** Autogenerate diffs against whatever DB
  `DEV_DBURL` points at, so drift in your local DB shows up as spurious drops and
  alters. Delete anything that isn't yours.
- **Production's schema is not exactly `models.py`.** Some indexes there have other
  names: `question_grades`' unique index is `user_divid_course_idx` in production but
  `question_grades_key` locally. Create and
  drop indexes with `if_not_exists=True` / `if_exists=True`, and don't drop an index
  this migration didn't create.
- **Big, busy tables** (`useinfo`, answer tables, `user_courses`, progress tables):
  build indexes with `postgresql_concurrently=True` inside
  `with op.get_context().autocommit_block():`, since `CONCURRENTLY` can't run in a
  transaction. `c3d8f1a2b4e6_add_reading_progress_indexes.py` is the pattern.
- **Backfills are bounded.** A full-table `UPDATE` over `useinfo` locks production
  for minutes; limit the window, as `b7e2c4d91f3a` does with 30 days.
- **New columns are nullable or have a `server_default`**, so the migration doesn't
  fail on existing rows.
- **Write a working `downgrade()`.**
- Explain any non-obvious choice in the migration's docstring.

## Connection pool

- Never call `create_engine()` or `create_async_engine()` in request code. Each call
  makes a new pool that is never closed; it caused production pool exhaustion
  (`QueuePool limit ... reached`). Use `async_session`, or `sync_session` for sync code.
- Never run blocking I/O inside `async def` handlers; it stalls every request on that
  worker. Wrap sync DB work in `asyncio.to_thread`. That doesn't help with pandas:
  DataFrame work holds the GIL and stalls the event loop from a thread too. Aggregate
  and filter in SQL so the frame stays small.
- To diagnose: `pool_monitor.py` logs occupancy and loop lag every few minutes, and
  `GET /admin/health/pool` shows one process. A full pool with low lag needs a bigger
  pool (`DB_POOL_SIZE`); high lag means something is blocking the loop.

## Tests

DB tests live in `test/components/rsptx/db/`. Use the session-scoped fixtures there
(`test_user`, `test_course`, `overview_course`), which depend on `init_test_db`. The
test DB is dropped and recreated for each run, so run only one DB test session at a
time.
